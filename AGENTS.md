# Разработка Forge

Этот файл описывает устройство репозитория и правила работы для людей и coding agents. Прямые указания пользователя определяют задачу; этот документ не создаёт дополнительных запретов или процедур согласования. Лицензионные условия находятся в `LICENSE`, границы ядра — в `CORE.md`, руководство по игровому API — в `Инструкция.md`.

## Философия и критерии решений

Forge — универсальный модульный движок на C++17 с игровыми сценами и скриптами на Python, поддержкой macOS и Windows. Один runtime должен подходить для 2D, 3D, новелл, хорроров и других проектов. Не встраивайте правила отдельной игры, жанра, структуру меню или сюжет в ядро.

- Простая игра должна требовать конфигурацию и сцену, а не изменения C++ или обязательного подключения всех подсистем.
- У новых возможностей должны быть понятные defaults, небольшой публичный API и самостоятельные модули. Расширения должны дополнять существующий рабочий путь.
- Все исходники доступны для изучения, изменения, адаптации и создания производных проектов согласно лицензии. Не вводите закрытые компоненты, скрытые проверки атрибуции или обязательные сетевые сервисы.
- Любую точку вне перечня ядра можно менять, заменять, расширять, перемещать или удалять при сохранении нужных проекту контрактов и сторонних лицензий. Расположение в `engine/` само по себе не делает файл ядром.
- Ядро тоже можно изменять. Обычным разработчикам игр рекомендуйте конфигурацию, публичные API и расширения: это облегчает обновления. Для разработки движка, исправлений ошибок и необходимых новых контрактов правки ядра допустимы без отдельного согласования.
- Сохраняйте работоспособность прежних проектов. Не меняйте смысл существующего API или defaults молча; несовместимость должна быть обоснована, документирована и сопровождаться способом перехода.

## Точная граница ядра

Закрытый перечень этой версии, определённый `LICENSE`:

| Файл | Ответственность |
| --- | --- |
| `engine/src/main.cpp` | CLI, запуск и изолированный CPython, выбор проекта/пакета |
| `engine/src/config.cpp` | Конфигурация, пути и проверки проекта |
| `engine/src/log.cpp` | Терминал, файловый журнал, открытие ошибок |
| `engine/src/runtime.cpp` | Цикл игры, Python bridge, lifecycle и hot reload |
| `engine/include/forge/engine.hpp` | Общие контракты runtime и модулей |
| `tools/packager.py` | Самостоятельная упаковка через embedded Python |

Перемещение, переименование или копирование кода ядра не меняет его лицензионный статус. Не расширяйте этот перечень неявно и не называйте всё C++-дерево неизменяемым ядром.

Если задача требует правки ядра, внесите её, укажите затронутый контракт и причину, обновите документацию и выполните относящиеся к изменению проверки. Рекомендация избегать таких правок для игр не является блокировкой или требованием запросить разрешение у пользователя.

## Карта исходников и поток выполнения

`tools/forge.py` — удобный launcher. `compile` собирает движок через CMake; нативный `forge` читает конфигурацию, проверяет проект и выполняет `validate`, `run`, `dev`, `edit` или `build`. `dev` использует уже собранный C++ runtime и обновляет игровой контент без упаковки. После изменения C++ нужна компиляция. `build` создаёт самостоятельную поставку с приватным Python; это отдельная операция от сборки C++.

| Путь | Назначение и граница изменений |
| --- | --- |
| `engine.json` | Конфигурация встроенного проекта: начальная сцена, paths, расширения, окно, локализация, storage, аудио, бюджеты |
| `engine/src/world.cpp` | Изменяемые объекты, AABB-физика, контакты, raycast, перемещение персонажа |
| `engine/src/render.cpp` | Изменяемый OpenGL-рендерер, текст, batching, камеры/FBO, свет, тени, ImGui-редактор |
| `engine/src/audio.cpp` | Изменяемое аудио: каналы, fades, spatial/DSP, голоса, транзакции |
| `engine/src/assets.cpp` | Фоновая загрузка, handles/pins, CPU-кеш, бюджет |
| `engine/src/model.cpp`, `engine/include/forge/model.hpp` | Импорт моделей, материалы, иерархия, skeletal animation |
| `engine/src/features.cpp` | Дополнительные bindings и проверки ввода/рендер-настроек |
| `engine/src/localization.cpp`, `engine/include/forge/localization_data.hpp` | Переводы, fallback, CLDR cardinal rules; сохраняйте Unicode notice |
| `engine/src/platform.cpp` | Пользовательские каталоги, crash reports |
| `engine/include/forge/gl.hpp`, `numeric.hpp` | Загрузчик OpenGL и числовые проверки; не входят в перечень ядра |
| `graphics/` | Изменяемые GLSL-шейдеры, исходный шрифт и отдельная лицензия |
| `modules/` | Библиотека для игр: UI/меню/диалог, saves/settings, audio/subtitles, input/replay, assets, animation, character, AI/events/math; пример C++-расширения |
| `scenes/`, `scripts/`, `objects/` | Встроенные сцены, Behavior, startup, JSON-шаблоны объектов |
| `textures/`, `materials/`, `models/`, `audio/`, `locales/` | Исходные ресурсы встроенных примеров и переводы |
| `tools/dependencies.py`, `vendor/dependencies.lock.json` | Фиксированные зависимости с SHA-256; скачанное содержимое не хранится в Git |
| `CMakeLists.txt`, `.github/workflows/build.yml` | Сборка и CI macOS/Windows |
| `tests/` | Регрессии native runtime, упаковки, чисел, графики; fixtures остаются в исходниках |
| `README.md`, `Инструкция.md`, `docs/FORGE_2.md` | Установка, публичный API, ограничения, карта тестового покрытия |
| `LICENSE`, `NOTICE`, `CORE.md`, `ATTRIBUTION.md`, `THIRD_PARTY.md` | Происхождение, атрибуция, лицензии |

Встроенные примеры: `welcome.json`/`welcome.py` (2D), `world3d.py` (3D), `interface.py` (UI, меню, слоты, языки), `advanced.json`/`advanced.py` (расширенные подсистемы), `editor-empty.json` (начало авторской сцены). Они — часть чистого движка. Не удаляйте их как «тестовую игру» и не подменяйте контентом пользовательского проекта.

`render.cpp` объединяет несколько крупных подсистем, а `runtime.cpp` — bindings и orchestration. Новую независимую логику по возможности выносите в отдельный изменяемый модуль. Архитектурные рефакторинги выполняйте в рамках задачи и с сохранением поведения.

## Конфигурация и расширения

- Пути к игровым папкам задаются через `engine.json`. Не зашивайте имена папок, абсолютные пути автора, текущую рабочую папку, конкретную игру или ОС в публичную логику. У групп paths есть контракт; переназначение папки не означает переименование ключа API.
- Игровые пути после нормализации должны оставаться внутри корня проекта. Пользовательские каталоги разрешайте через storage/user-path API, а не через обход корня проекта. Проверяйте также символьные ссылки и назначения копирования.
- Должны работать пробелы и Unicode в путях/аргументах на обеих ОС. Используйте `std::filesystem`, существующие UTF-8/UTF-16 переходы, `pathlib` и явную кодировку текстовых файлов.
- Сначала используйте `modules/`, публичный `import forge`, конфигурацию и события. Для низкоуровневого расширения есть `FORGE_MODULE` и `native_modules`/`FORGE_MODULE_SOURCES`; Python-контент не должен требовать их компиляции.
- Общие возможности оформляйте независимо от примеров. Объекту, сцене и игровому контроллеру не следует знать внутренности редактора или конкретного меню.
- Новые необязательные поля должны иметь defaults, проверку типов/диапазонов и описание. Версии конфигурации, save/replay-форматов и движка имеют разный смысл; не повышайте их вместе автоматически.
- Текст интерфейса передавайте через переводимые ключи и параметры. Поддерживайте переключение языка, fallback и множественные формы, не копируйте реализацию локализации в каждую игру.
- Следуйте стилю изменяемого файла. Не совмещайте исправление с массовым форматированием, переписыванием соседних API или обновлением всех зависимостей.

## Инварианты runtime и ресурсов

### Объекты, ввод и hot reload

- JSON, Python spawn/build и setters должны согласованно проверять данные до изменения состояния. NaN/Infinity и неверные формы векторов не должны попадать в физику, камеру или рендерер.
- Конечность входа не гарантирует конечность результата: проверяйте reciprocal массы, промежуточные произведения, переполнение и границы до преобразования float/double в int. Физика должна сохранять прежнее допустимое состояние при отказе.
- Активность коллайдеров должна определяться общей логикой для solver, raycast и character controller, с учётом 2D/3D.
- Создание и уничтожение объектов внутри lifecycle callbacks не должно инвалидировать обход. `on_destroy()` вызывается однократно; подписки и callbacks старой сцены освобождаются.
- Пауза игры, отключение физики и работа UI — отдельные возможности. Не останавливайте UI/настройки или нужные аудио-процессы только потому, что игра на паузе.
- Hot reload готовит кандидата и только после проверки заменяет рабочее состояние. При отказе сохраняйте прежние объекты, импорты, paths, локализацию, аудио, настройки окна и подготовленные графические ресурсы.
- `sys.path` принадлежит также чужим модулям: удаляйте только пути, которыми управляет Forge; не накапливайте дубликаты и не оставляйте пути отменённой конфигурации. Проверяйте `sys.modules` и namespace packages при смене каталогов.
- Записи saves/предпочтений через управляемые API откладываются до успешного commit. Не обещайте откат произвольного Python I/O, сетевых запросов или внешних сервисов; прямые побочные эффекты требуют отдельной стратегии игры.
- Новые listeners, handles и голоса отменённого кандидата освобождаются; callbacks не должны удерживать старую сцену бессрочно.

### Графика, assets и аудио

- CPU-загрузку можно выполнять в workers; OpenGL и GPU-upload — на потоке с текущим контекстом. Соблюдайте lifetime объектов и snapshot путей для фоновой работы.
- Сохраняйте ограничения budgets, pins и LRU; сообщайте отказ явно. CPU-cache budget не является гарантией лимита всей памяти процесса, особенно во время декодирования.
- `validate`/`build` проверяют весь проект; `run`/`dev` подгружают будущие ресурсы по требованию. Проверка текущей сцены перед commit должна исключать частично применённый renderer.
- Измерение и отрисовка текста используют одинаковые метрики/fallback. Raster-size ограничивайте до небезопасных произведений/преобразований; учитывайте HiDPI.
- Batching/atlas оптимизация не должна ломать порядок прозрачности, clipping, UV, материалы и shader uniforms. Проверяйте фактические пиксели и diagnostics.
- Аудио сохраняет channel gains, voices, cursor и настройки при откате. Silent/headless режим не подтверждает работу реального устройства; DSP и streaming должны иметь явные ошибки/диапазоны.
- Состояние редактора не равно произвольному Python-состоянию игры. Сохраняйте JSON-контракты и не обещайте сериализацию любого пользовательского объекта.

### Persistence, упаковка и диагностика

- SaveManager: версия формата, checksum/валидация, atomic write, backup и миграции должны оставаться согласованными. `info()` и меню учитывают восстановление из одного backup так же, как `read()`.
- Проверяйте все источники упаковки, включая `python_paths`, а не только `paths`. Output не должен заменять проект или находиться внутри копируемого каталога; каждое назначение отдельно остаётся внутри stage.
- Не перезаписывайте существующую сборку автоматически. Поддерживайте изолированный комплектный Python и запуск из другой папки без помощи внешних `PYTHONHOME`/`PYTHONPATH`.
- Пакеты сохраняют лицензии, notices и проверяемый manifest. На macOS учитывайте Mach-O relocation/подписи и `.app`, на Windows — Python/DLL, Unicode argv и runtime-зависимости.
- Ошибки сборки/запуска попадают в терминал и журнал с полезным контекстом. В runtime сохраняйте traceback/diagnostics и открытие лога согласно настройке; тесты используют `--no-open-log`.
- Пользовательский `forge.log()` одновременно работает в терминале и файле. В режиме user storage не записывайте данные внутрь подписанной игры.
- Crash reporter по умолчанию ничего не отправляет. Не добавляйте сетевой сбор пользовательских данных. Fatal handler остаётся минимальным и не выполняет небезопасную обработку Python/JSON.

## Подготовка и воспроизводимые проверки

Все команды выполняются из корня исходного репозитория. Чистый checkout не содержит `.tools`, `build`, `dist` и скачанных библиотек. Нужны Python 3.10+ с development headers, CMake 3.24+, OpenGL 3.3 и нативный C++-компилятор. Версия CMake в текущей инструкции/CI закреплена на 3.31.6.

macOS, после установки Command Line Tools и подходящего Python:

```sh
python3 -m venv .tools
.tools/bin/python -m pip install cmake==3.31.6
.tools/bin/python tools/dependencies.py
.tools/bin/python tools/forge.py compile
.tools/bin/python tools/forge.py validate --no-open-log
.tools/bin/ctest --test-dir build -C Release --output-on-failure
```

Windows, Python x64 и Visual Studio 2022 Build Tools / Windows SDK, Developer PowerShell:

```powershell
python -m venv .tools
.tools\Scripts\python.exe -m pip install cmake==3.31.6
.tools\Scripts\python.exe tools/dependencies.py
.tools\Scripts\python.exe tools/forge.py compile
.tools\Scripts\python.exe tools/forge.py validate --no-open-log
.tools\Scripts\ctest.exe --test-dir build -C Release --output-on-failure
```

После активации окружения ниже можно писать `python` вместо его полного пути. При непосредственном вызове тестов укажите существующий бинарник: macOS обычно `build/bin/forge`; Windows — `build/bin/Release/forge.exe` при multi-config generator либо `build/bin/forge.exe` при single-config.

| Проверка | Команда / условия |
| --- | --- |
| Числа и пути без GUI | `ctest --test-dir build -C Release --output-on-failure -R "^(numeric\|packager_paths)$"` |
| Реальный Python bridge и lifecycle/reload | `python tests/integration.py <binary>` |
| Подсистемы 2.0 и поставка | `python tests/features.py <binary>` |
| Оба интеграционных набора через launcher | `python tools/forge.py test` (не заменяет numeric/packager_paths) |
| UI/текст/GLSL/audio-device | `python tests/graphics.py <binary>`; реальный desktop/OpenGL и аудиоустройство |
| Камеры/UV/batching/тени/skinning/editor | `python tests/features_graphics.py <binary>`; реальный desktop/OpenGL |
| Контент без окна | `python tools/forge.py run --headless --frames 30 --scene advanced.json --no-open-log` |
| Ручные примеры | `python tools/forge.py dev --scene interface.py`, `dev --scene world3d.py`, `dev --scene advanced.json`, `edit --scene editor-empty.json` |
| Самостоятельная поставка | `python tools/forge.py build --output dist/ReviewGame`; на macOS также новый путь `dist/ReviewGame.app` |

CTest регистрирует numeric, packager_paths, integration и features. Несмотря на headless игровой цикл, macOS-тест `.app` в features вызывает системные `sips`/`iconutil`/`codesign`; ограниченное окружение может требовать доступа к этим сервисам. Графические тесты отдельно и не входят в эти четыре набора. `tests/ui_components.py` и `tests/model_fixture.py` — помощники проверок, а не самостоятельные unittest entry points.

Выбирайте проверки по риску изменения:

- Для документации и Git-гигиены достаточно проверки diff, ссылок, ignore/index и ресурсов в чистой поставке; не добавляйте тесты, повторяющие текст документации.
- Для поведения добавляйте регрессию воспроизводимого отказа на публичном API; не ограничивайтесь mocks, если важен C++/embedded Python.
- Для C++ соберите движок и выполните относящиеся native/integration tests. Для lifecycle, reload, persistence или упаковки проверяйте и успех, и отказ с сохранением прежнего состояния.
- Для графики проверяйте реальные кадры, ошибки ресурсов и восстановление; headless не подтверждает результат OpenGL. Для звука отдельно проверяйте устройство при затронутом playback/DSP.
- Для зависимости/packager/release проверьте standalone launch из другой папки, лицензии, hashes и приватный Python. Developer ID/нотарификация требуют собственных credentials и не выполняются ради обычной проверки.
- CI сейчас собирает macOS и Windows, запускает launcher test и directory build. Это не включает отдельные GPU-тесты или автоматическую нотарификацию; результат одной ОС не доказывает работоспособность другой.

После успешных необходимых проверок не расширяйте их без новой причины. В отчёте указывайте реально выполненные команды, результаты и существенные непроверенные платформы/условия.

## Чистота Git и поставки

В Git остаются исходники, публичная документация, инструменты, CI, тесты, исходные fixtures, lock-файл, лицензии и встроенные примеры со всеми ресурсами. Это исходная поставка движка, а не снимок установленного окружения.

- Не добавляйте `.tools`/venv, build/CMake cache, dist/`.app`, загруженный vendor, bytecode, saves/backup, preferences, logs, crash reports, replay-записи, captures и персональные IDE-файлы.
- Для локальных кадров/отчётов используйте игнорируемые `artifacts/`, `Проверка.md` или точные локальные пути. `docs/FORGE_EXPERIENCE.md` — локальный внешний отчёт, исключённый из чистой поставки; он может отсутствовать. Публичные документы не должны зависеть от него или скриншотов.
- Не копируйте частную игру, её сохранения, историю использования, локальные абсолютные пути и credentials в стартовый контент. Отдельную игру создавайте через `init --output <empty-directory>` и выбирайте её `--project`.
- Не исключайте все `.obj`: здесь это также исходные Wavefront-модели. JSON, GLSL, glTF, PNG, TTF и WAV тоже могут быть необходимыми исходными ресурсами.
- Новые storage/capture-пути добавляйте в `.gitignore` точечно. Не игнорируйте неизвестные папки глобально только ради скрытия текущего `git status`.
- При очистке отслеживания локальных результатов предпочитайте `git rm --cached`, сохраняйте файлы на диске и проверяйте ссылки. `.gitignore` сам не удаляет файлы из индекса или истории.
- Не переписывайте историю Git, не удаляйте пользовательские изменения и не публикуйте/push без соответствующего указания. Очистка текущего индекса не очищает прошлые коммиты.
